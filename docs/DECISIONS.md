# Журнал решений (ADR)

## D-001: Цель — личный учебный инструмент, не продукт на продажу
Принято 2026-09-13. Влияет на всё: дрилл важнее библиотеки ответов; UI ориентируется
на GTO Wizard, но не копирует; скорость решения одного спота важнее покрытия.

## D-002: Мультиway = компас, не GPS
Принято 2026-09-13. Мультиway-выдача обязана нести метрики волатильности (разброс
сидов). Не называть мультиway-результаты "равновесием" — только "блюпринт/приближение".

## D-003: Дрилл-луп — главная фича
Принято 2026-09-13. Цикл "предположил -> решил -> увидел потерю EV -> понял почему" —
ядро продукта. Солвер без дрилла считается недостроенным.

## D-004: Порядок фаз по убыванию доверия
Принято 2026-09-13. ICM -> пуш/фолд -> постфлоп HU -> префлоп-блюпринт -> мультиway.
Сначала блоки, где можно быть точными и заслужить доверие пользователя.

## D-005: Порядок изменения приоритетов
Принято 2026-09-13. Приоритет меняется только коммитом в ROADMAP; агент не меняет
план молча; агент обязан возражать при предложениях, ломающих план, а не поддакивать.

## D-006: Абстракция карт для стратегического пространства постфлопа
Принято предварительно (2026-09-13): точные комбо остаются для equity/blockers
(принцип репозитория не ломается), стратегии живут в бакетах. Интеграция за флагом,
exact-режим сохраняется для тестов. Уточнить при чтении кода.

## D-007: Эксплуатируемость — единственная валюта качества HU-решений
Принято 2026-09-13. Число от best-response-замера печатается в каждом отчёте.
Приближённый probe из foundation доводится до честного замера в T4.2.

## D-008: ICM считает в f64
Предварительно (2026-09-13): вероятности природы дробные; на границе с целыми Chips —
явная конверсия. УТОЧНИТЬ при виде реального кода Chips (crates/holdem-domain).


## D-009: Bubble API — индексы игроков и явная семантика вылетов
Принято 2026-09-13. Игроки идентифицируются индексами, а не значениями стеков
(равные стекы двусмысленны). Вылет (нулевой стек после all-in) = последнее
место; приз за него = payouts[n-1] при m == n (финалка), иначе 0; оставшиеся
игроки делят усечённые призы. All-in переход — только пара hero/villain,
прочие стеки неизменны (стандартная аппроксимация ICMIZER/HRC).

## D-010: Делегирование технических решений агенту (восстановлено)
Восстановлено 2026-09-24 (сессия 13). Норма существовала устно с первой смены
(агент держал её как рабочее правило), но записи в журнале не имела —
нумерация прыгала D-009 -> D-012. Норма: выбор технических средств
внутри задачи (алгоритмы, структура кода, места врезок, утилиты) —
зона агента; пользователь держит вето на результат (тесты, зелёность,
соответствие плану) и приоритеты. Агент обязан возражать при
предложениях, ломающих план (D-005), и фиксировать значимые решения
записями D-xxx; восстановление устной нормы постфактум — как здесь:
с пометкой и датой.

## D-012: Верификация пуш/фолд — epsilon-равновесие, а не таблица из памяти агента
Принято 2026-09-13. DoD T2.1 изменён: вместо сверки с «Nash-таблицей» (источника
которой в репозитории нет, а память агента на конкретные проценты ненадёжна)
решение проверяется математически самодостаточно: max regret в bb против
финальных стратегий + структурные якоря (AA пуш, 72o фолд, монотонность по
стеку). Точные сверки с внешними таблицами — только через fixtures из
доверенного источника, добавленные пользователем.

## D-013: Численные гейты качества — только из фикстур
Принято 2026-09-15. Пороги и коридоры из памяти агента запрещены (инцидент:
два разных коридора для одного числа за одну сессию). Допустимые гейты:
точные якоря эквити, инварианты, структурные свойства; внешние численные
сверки — только через fixture из доверенного источника, добавленный
пользователем. Самосогласованная exploitability против шумной матрицы
не является доказательством правильности.

## D-014: Точная матрица 169x169 отложена; сейчас — точечная верификация
Принято 2026-09-15. Полный перебор для всех пар классов ~48e9 оценок рук —
часы на текущем оценщике. Принято: (1) exact_equity для конкретных матчапов
— сейчас (C(48,5) = 1 712 304 борда, секунды); (2) сверка подозрительных
ячеек production-матрицы с точными значениями — сейчас; (3) полная точная
матрица — отложена до быстрого оценщика (Фаза 3) либо overnight-прогона
по отдельному решению. Примечание: crates/equity exact_profile_equity не
поддерживает префлоп (не более 2 неизвестных карт борда), поэтому перебор
реализован в pushfold поверх собственного оценщика, валидированного
фикстурами (AA-KK 81.9 и др.).

## D-015: Перезапись файлов — только с верифицированно свежей базы
Принято 2026-09-15. Инцидент сессии 9: фетч main.rs в сессии 6 вернул
устаревшую версию, перезапись по ней удалила команду icm (регрессия
жила с f56f046). Попутно: «дефолт матрицы 20000» сессии 7 менял мёртвый
unwrap_or при реальном дефолте 200 в parse. Правила: перед перезаписью
сетевого файла сверять маркеры свежести (известные фичи последних
коммитов); при сомнении файл вставляется пользователем текстом;
изменения «по умолчанию» проверяются по фактическому пути кода.
Урок StrictMode: переменные состояния инициализируются до первого
ветвления, без исключений.

## D-016: T2.2 (multiway пуш/фолд) отложен; Фаза 3 стартует
Принято 2026-09-15. Основание — бенчмарк T3.0 (i5-2500K, 4 ядра, ~2.3M
семикарточных оценок/с): multiway MCCFR-блюпринт на этом железе — высокая
цена при шумном результате, а учебная ценность multiway пуш/фолда закрыта
связкой «HU-сетка (pushfold CLI) против критического коллера + ICM bubble
factor (icm CLI)». D-003 (дрилл — главная фича) требует постфлоп HU
следующим блоком. T2.2 возвращается в план опционально после Фазы 4.

## D-017: Эквити-уточнение флоп-бакетов — exact-перебор, якоря, квантили
Принято 2026-09-23 (сессия 11). План сессии 10 предполагал MC с фиксированным
сидом; после чтения реального API (exact_profile_equity: на флопе
C(45,2) = 990 runouts на матчап) выбран точный перебор — нулевой шум,
структурный детерминизм без RNG. Решения:
(1) якоря — 6 матчапов (роли в коде): AA-KK, JJ-AKo, 87s-AKo, AKs-QQ,
    22-AKo, 99-TT; якорь недоступен, только когда его парный ранг —
    ранг трипса борда; инстанцирование на представителе класса —
    фиксированные правила (пара: первые свободные масти; suited:
    предпочтение масти борда; offsuit: первые свободные разные);
(2) агрегат — среднее z-оценок доступных якорей; среднее/сигма по всем
    1755 классам с весами кратностей флопов (trips/monotone 4, paired
    и two-tone 12, rainbow 24; сумма 22100 = C(52,3) — выводится
    тестом); группы — взвешенные квантили фактического распределения,
    по умолчанию 4, из конфига; порогов из памяти нет (D-013);
(3) бакет = бакет_v1 * группы + группа; v1 нетронут (fingerprint v1
    неизменен — байтовая регрессия в смоке); fingerprint эквити-режима:
    тег режима + гранулярность + число групп + имена якорей + бакеты;
(4) размещение: crates/abstraction/src/equity.rs поверх v1, path-dep
    на holdem-equity (+ dev holdem-cards); CLI flop-clusters --equity
    [--equity-groups N], по умолчанию выключен, помечен тяжёлым;
(5) замер: 1755 x 6 x 990 x 2 = 20.9M оценок — 123 c (release-тест) /
    131 c (CLI) на reference-машине; прогноз «9-45 c» был ошибочен:
    бенчмарк T3.0 — end-to-end CLI, не throughput оценщика (реальный
    ~170k оценок/с в пайплайне); будущие прогнозы — от замера, не от
    T3.0; оптимизация прохода (аллокации score_runout — чужой крейт
    equity; кэш, параллелизм) — отдельной задачей при потребности;
(6) тёрн/ривер-бакетинг — следующий кусок T3.1 на том же механизме.
Численные гейты — только структурные (инварианты, детерминизм
fingerprint); полный проход — #[ignore] release-тест (прецедент D-014).

## D-018: Тёрн/ривер-бакетинг — плоские канонические классы улиц на механизме D-017
Принято 2026-09-23 (сессия 12). (1) Улица = канонический класс n-картного борда
без порядка прихода карт: тёрн 16 432 класса, ривер 134 459 — вывод
Бернсайда, подтверждён brute-force сверкой всех C(52,4) = 270 725 и
C(52,5) = 2 598 960 бордов; переходы флоп->тёрн->ривер — задача T3.2.
(2) Канонизация: минимум по 24 перестановкам мастей от множества карт;
при совпадающих рангах наивный подсчёт паттернов по разбиениям позиций
завышает классы (квады = 1 борд, не 24) — классы генерирует код,
кратность = размер орбиты, гейт — инвариант суммы кратностей = C(52,n).
(3) v1 — структурные бакеты: семейство ранговых мультиплетов x форма
мастей x top/mid/span-группы Granularity (общие хелперы lib.rs).
v2 — те же 6 якорей D-017 из общего pub(crate)-ядра equity.rs (одни
якоря на всех улицах, расхождение копиями исключено), z-агрегация с
весами кратностей, взвешенные квантили, бакет = v1*G + g, fingerprint
с тегом улицы. Рефактор ядра прошёл под гейтом регрессии: fingerprints
флопа из AI_LOG сессии 11 закреплены пинами в тестах и совпали
байт-в-байт. (4) Ривер: эквити якоря дискретно {0, 0.5, 1} —
структурное свойство полного борда (std ~0.5 ожидаем); доступность
якорей на 4/5 бордах богаче правила трипсов флопа (квады блокируют и
пары, и бродвей) — проверяется инстанцированием, counts наблюдаемые.
(5) Замеры (release, i5-2500K): генерация классов тёрн ~0.3 c / ривер
~2.4 c (brute-force сверка ривера 4.8 c); эквити-проход тёрн ~50 c /
ривер ~10 c — прогноз от базы ~170k оценок/с (D-017(5)) подтверждён.
(6) CLI turn-clusters / river-clusters [--equity] [--equity-groups N] —
зеркало flop-clusters; флоп не меняется. (7) Контракт rep ядра эквити:
ровно карты борда, без паддинга 0xFF из [u8;5] классов улиц — баг
паддинга пойман debug-тестами до коммита; при T3.2 кандидат на замену
типом Board<'a>. Численные гейты — только структурные (инварианты,
brute-force сверки, детерминизм fingerprint); полные проходы —
#[ignore] release-тесты.

## D-019: Интеграция абстракции карт — пост-строительный трансформ дерева за флагом
Принято 2026-09-24 (сессия 13). (1) Механизм: GameTree -> GameTree одним
нисходящим проходом (crates/solver/src/card_abstraction.rs); на
chance-узле исходы группируются по бакету итогового борда улицы
(абстракции T3.1), представитель — лексикографически наименьшие карты,
вероятность — сумма членов, масса сохраняется без ренормализации;
не-представители отбрасываются. Компиляторы/солверы/чекпойнты не
меняются: fingerprint считается от трансформированного дерева, инфосеты
сливаются физически, комбо точные (D-006). (2) Точка интеграции —
единая для всех путей: solve() и CLI/job-store идут через
build_solver_with_abstraction (урок инцидента: unit-тест на том же
входе, что интеграция, не ловит пропущенный production-путь; ловит
end-to-end смок на реальном исполнителе). (3) Цена абстракции — числом
в каждом отчёте (требование пользователя): CardAbstractionReport —
структурные счётчики исходов до/после по улицам; блок blocking — MC-
оценка потери массы из-за блокировки представителей дилами
(estimate_representative_blocking: сэмплер дилов, детерминированный
seed-поток, отличный от солверного; натуральные блокировки не в счёт;
ветви действий — равновероятное приближение; финальная мера —
best_response_probe, T4.2). (4) Флаг: chance.card_abstraction
{ mode, granularity, equity_groups, blocking_samples } в spot-JSON;
mode и granularity обязательны — дефолтного режима нет; отсутствующий
флаг = точный режим, путь трансформа не вызывается. Схема без bump
(опциональное поле). (5) Задокументированные границы: unknown
mode/granularity парсятся мягко в structural/fine — долг валидации;
MC-оценка не пересчитывается при resume (зависит от дерева/спеки, не
от итераций); single-outcome chance-узлы не попадают в группировки и
не дают потери по определению. (6) Эталоны (release, i5-2500K): чек-ин
8max — exact не задет, tree_fingerprint 13077678885480782512 (пин);
абстрагированный — 270 chance-узлов по 1 исходу: слияний нет,
lost_fraction 0.0 (deals 118) — структурно честный ноль. Рукотворный
3-max (As Ks Qs / Ah Kh Qh / 2d 7d 9c; AKs/KQs/QQ; coarse):
outcomes 46 -> 42, flop_fingerprint 15917378774416862389, deals 64,
lost_fraction 0.03125 — слияние и потеря доказуемо видны в
production-пути. (7) Q-2 закрыт: peak working set 26.8 MB при 1500
итерациях полного 8-max solve — RAM-потолка нет.

## D-020: Постфлоп-стартующие споты — поле board, реплей границ улиц, certain-карты
Принято 2026-09-24 (сессия 14, T4.1). (1) Схема: опциональное поле `board`
(строка карт) в job-JSON; отсутствует/пусто — префлоп-старт, прежний путь
байт-идентичен (прецедент D-019(4)); 3/4/5 карт — старт на флопе/тёрне/
ривере; schema_version не поднимается. (2) Механизм: конфиг несёт
board_cards: Vec<Card>; state_after_history потребляет карты на закрытых
раундах (actor == None, терминала нет) через advance_to_next_street с
эффективным порядком (явный postflop_order Full-конфига, иначе
table.postflop_order() — как в build_tree); build_full не меняется: корень
с actor — штатная ветка. (3) certain-карты: маска карт, гарантированно
выходящих на борд — стартовый борд плюс карты, присутствующие во всех
явных исходах каждой ДОСТИЖИМОЙ улицы (фиксированные ранауты); улицы,
пройденные стартовым бордом (длина >= 3/4/5), пропускаются — их исходы
мёртвый конфиг (JSON-слой отвергает на парсинге, конфиг-слой терпит, как
до T4.1). Маска вливается в dead_cards в into_config и объединяется на
входе BatchSolver (build_solver, build_solver_from_tree, MC-оценка
блокировки): сэмплер не генерирует невозможные дилы; конфликты fixed-карт
с dead_cards и hero-руками — жёсткие ошибки. Происхождение: интеграция
solve-смока — фиксированные ранауты 5h/3h при широком SB (100%) давали
«private profile has no legal public outcomes» (единственный исход улицы
блокируется рукой дила, прунинг оставляет пустоту); многоисходные улицы
не затронуты — пересечение исходов пусто, прунинг/ренорм per-deal в
компиляторе корректен. 8max-пример не затронут: его диапазоны не содержат
карт ранаутов, фильтрация пуста, tree_fingerprint не меняется. (4) Строгая
валидация (ошибки, не молчание): длина борда не из {0,3,4,5}; конфликт
борда с dead_cards; конфликт hero с бордом; префлоп-сайзинг и явные
исходы пройденных улиц при постфлоп-старте; исходы достижимой улицы,
пересекающие ранние публичные карты. (5) Развилка 2-игроков закрыта
выбором A: SRP BTN vs BB — 3-max с фолднутым SB (BTN=0/SB=1/BB=2):
пот 5.5bb при опене 2.5bb, карты SB сдаются и блокируют ауты (payoff
требует hands == table_size), продукционная поверхность переиспользуется;
HU-гварды (3..=8 в multiway_spot.rs и multiway_holdem.rs) — отдельной
задачей (домен 2..=8 и HU-порядки готовы). (6) Round-режим с бордом
разрешён (RoundComplete — инспекция раунда); Full — для решения.
(7) Переменный борд (история на границе улицы — шанс-корень) не входит:
нужна hero-агрегация ниже шанс-корня — ступень после T4.1; Board<'a>
не тронут — долг открыт. (8) Замеры (release, i5-2500K): validate SRP
0.027-0.037 c; узлы 1175/3687/6943 при 1/2/3 bet-фракциях; регрессия
8max tree_fingerprint 13077678885480782512 — байт-совпадение с пином
сессии 13; solve-смок SRP (200 итераций): exit 0, 6 c, tree_fingerprint 8033291308632370283, observed_hands 4995. Диапазоны
SRP-примера — демо-заполнители (в построение дерева не входят), SB —
100% (реальный card removal); уточнение — к T4.3.

## D-021: Честная эксплуатируемость — вилка sampled-BR (two-pass)
Принято 2026-09-24 (сессия 15, T4.2). (1) Вердикт по существующему
best_response_probe: per-deal omniscient BR — в узлах цели max по детям
при известных чужих картах; по Йенсену систематически завышает
эксплуатируемость; доки это признавали («approximate», «diagnostic
signal, not an exploitability proof»). Требование D-007 — честный замер.
(2) Механизм: exploitability_probe — two-pass на клоне сэмплера (поток
детерминирован состоянием: одинаковый чекпойнт -> одинаковый отчёт, в
т.ч. после resume). Pass 1 (поиск): омнисциентная рекурсия накапливает
per-инфосет значения действий (V-таблица), политика = argmax
накоплений. Поиск — жадный/оптимистичный; измерение — несмещённое;
смещение поиска влияет на ширину вилки, не на валидность нижней
границы. Pass 2 (измерение): свежие дилы того же потока — фиксированная
политика против средней; непосещённые инфосеты — консервативный
fallback на среднюю. (3) Вилка: нижняя граница = paired improvement
фиксированной реализуемой политики (реальный эксплойтер, выигрывающий X
у профиля — то, чему можно верить в дрилле); верхняя — парная
(per-deal omniscient − средняя, Йенсен); поточечный инвариант
upper >= fixed на каждом диле — структурно (max >= выпуклая комбинация),
гейтится жёсткой ошибкой, без допуска. (4) Единицы: слой batch — фишки;
слой spot нормирует в bb (÷ big_blind) и % банка корня спота (÷ pot ×
100); headline = max по игрокам paired improvement (прецедент pushfold),
SE — консервативный max по игрокам. (5) Врезка: execution.
exploitability_samples (serde-default 128 по замеру: ~0.08 c/сэмпл
верхней границы, two-pass ~1.5-2x — секунды поверх солва; 0 = выкл,
байт-идентичность JSON без сэмплов — жёсткий тест) + CLI --br-samples
поверх (прецедент --utility-samples, арм — трансформация существующего);
единая точка — result_from_solver_with_abstraction (урок D-019(2)) —
solve() и CLI/job-store получают число одним путём; блок exploitability
в result-JSON без bump схемы (прецедент D-019(4)). Существующий
best_response_probe не тронут (верхняя граница используется из нового
метода; API и тест сохранены). (6) Замеры (release, i5-2500K): SRP-спот,
200 итераций: замер стоимости 16/64/128 = 1.31/5.26/10.11 c (верхняя
граница, линейно); solve-смоук с замером: 30 c, improvement
116.10734426454177% pot (SE 148.9275541172863), upper 375.8802564712396% pot, __HANDS__ observed
hands; resume + --br-samples 16: 9.2 c; пин SRP tree_fingerprint
8033291308632370283. (7) V-таблица pass 1 — субстрат потери EV дрилла T4.3 (V* −
V(действие) при продолжении средней); здесь не реализовано. (8) Численные
гейты — только структурные (порядок вилки, детерминизм, конечность);
порогов из памяти нет (D-013). Долги enumerate×dead_cards и условность
явных исходов — вне ядра, отдельными правками (см. AI_LOG сессии 14/15).

## D-022: Дрилл v0 — механика в CLI; потеря EV paired conditioned-MC
Принято 2026-09-25 (сессия 16, T4.3). (1) Цикл D-003: спот показан (борд/
банк/позиция/рука), стратегия скрыта; ввод действия; честная потеря EV;
раскрытие частот средней стратегии этой руки; 10 рук, счёт, средняя —
в файле сессии (DoD). (2) Мера: paired conditioned-MC — рука hero
фиксирована, оппоненты по диапазонам; baseline = средняя везде;
forced = действие hero в корне + средняя ниже
(evaluate_public_fixed_policy с одноэлементной политикой — актив T4.2);
loss = baseline − forced на общих дилax, mean + парный SE
(update_online_moment). Несмещённая; V-таблица D-021(7) (смещение
поиска) не используется — субстрат оптимизации будущего. Единицы:
фишки / bb / % банка (нормировка слоя spot, прецедент T4.2). (3)
Механика: движок crates/solver/src/drill.rs (R3, файл-автор) — run_drill;
руки выбираются по весам hero-диапазона собственным XorShift64 от
execution.seed; сессия — JSON, атомарная запись после каждой руки +
финальная запись по завершении (файл существует при любом исходе);
q/EOF — выход с сохранением. Контракт персистентности: файл хранит
числа в кратчайшем repr; повторное чтение может смещать f64 на 1 ulp
(дефолтный парсер serde_json без float_roundtrip) — cross-JSON
сравнения в тестах структурные + допуск 1e-9, бит-в-бит через границу
сериализации не проверяется by design. sample_conditioned: ВСЕ руки
проходят конфликт-проверку, включая фиксированную руку hero (rejection
с пересэмплом остальных) — баг «фиксированная рука пушится без
проверки» пойман мини-гейтом на широких SRP-диапазонах; юнит-тесты с
непересекающимися диапазонами были слепы — тест-данные расширены
пересечением (BTN += Qs Qh); побочное доказательство работы фикса в
самих замерах: hero QsQh блокирует BTN QsQh -> все conditioned-дилы
идентичны -> SE=0; hero QdQc не блокирует -> BTN миксует -> SE>0.
Путь к фиксу занял четыре уровня (B9-B13), три ложных стопа — мои, все
пойманы гвардами до записи: широкий паттерн поймал валидатор пэйоффа;
гвард геометрии из головы вместо дампа; однострочный якорь против
fmt-разбиения vec!. Уроки: якорь обязан жить внутри целевой функции;
геометрия — только со строк дампа; якорь после fmt — из свежего дампа.
batch-солвер: drill_root_actions / drill_root_frequencies /
drill_hand_outcome. (4) CLI drill: REPL (нумерованные действия, q/EOF;
U+FEFF стрипается — измерено: PS-пайп несёт EF BB BF перед первой
строкой при $OutputEncoding=us-ascii, квирк PS 5.1), --job; --output =
файл сессии (дефолт <job>.drill.json), --job-dir обязателен;
--iterations = итерации солвера; --utility-samples = дилы на руку
(дефолт 256); число рук — константа 10 (DoD v0); ноль правок
CliOptions; замер эксплуатируемости в drill не считается; сборка
солвера — единый путь build_solver_with_abstraction (D-019). Прорыв
инцидента «unknown command»: путь команды в CLI начинается в parse_args
(белый список), run()-диспетчер — вторая половина; новые команды
добавляются в оба места, интеграционный CLI-смок с новым именем
обязателен. Смок-конвенция: stdin-смоки — file-redirect (cmd < файл с
явной кодировкой); PS-пайп — информационный тест: PS-пайп работает после BOM-стрипа и фикса сэмплера (hands=1).
UI — после Q-1 (перенос зафиксирован ROADMAP-коммитом 5321b25). (5)
Гейты: детерминизм (равные состояния солвера -> равные сессии — тест),

## D-023: Дрилл-UI — план A+ (редизайн оболочки -> дрилл в новую оболочку) и шаговый drill-API
Принято 2026-09-25 (сессия 17; Q-1 закрыт решением пользователя; запись
в журнал произведена закрывающим блоком сессии 17 — черновик до этого
существовал только в чате, см. инцидент сессии 17 №5).

(1) Решение: A+ = план движка A (принят дословно, п.2) + обязательный
UI-редизайн ДО врезки дрилла: (а) новая информационная архитектура по
спецификации п.3; (б) новая оболочка; (в) дрилл-вкладка — только в
новую оболочку, не поверх старого вида. Основания: D-003 (дрилл — ядро,
ему нужна скорость доставки, не платформа), D-001 (одиночный локальный
инструмент), ноль нового инструментария; существующие матрица/инспектор/
nodeNav/API-клиент переиспользуются переносом.

(2) Движок (A, дословно): шаговый API /v1/drill/*: POST /v1/drill/start
{job, job_id, hands, ev_samples} -> session_id + первый prompt (частоты
в prompt НЕ входят — reveal только после ответа); POST /v1/drill/{id}/
answer {action_index} -> {loss, frequencies, next_prompt | done};
GET /v1/drill/{id} — состояние сессии; POST /v1/drill/{id}/quit —
финализация. Серверный session-стор по конвенциям job-store: атомарная
запись после каждой руки, data-dir, лимит активных сессий. drill.rs:
responder-цикл -> шаговый DrillSessionEngine (next_prompt/submit_answer);
run_drill становится обёрткой над ним — CLI REPL не ломается. Reveal-
модель: сервер не отдаёт частоты руки до ответа на неё. Порог C
(ES-модули без сборщика, сервер отдаёт 4-6 .js): ~2000-2500 строк
index.html либо старт Фазы 7; B (SPA/сборщик) — отвергнуто.

(3) UI-спецификация (проверяемая):
  1. Матрица — герой: >=50% ширины; ячейки >=34-40px на 1080p
     (текущая 45px); МЕТКА РУКИ (A2o/K9s/77) крупно + частота доминанты
     меньшим кеглем + полоска микса; доминирующее действие — заливка.
  2. Спот-хедер над матрицей: позиция hero, борд карточными токенами,
     пот и эфф.стек в фишках И bb (1100/5.5bb), сегмент «спот» одной
     строкой (SRP · BTN open 2.5bb · SB fold · BB call), блайнды в
     шапке, мини-таблица позиций/стеков в сайдбаре, качество ответа —
     exploitability «<= X% pot» (число T4.2).
  3. Сайдбар сворачиваемый, два уровня: «частое» (диапазоны, стеки,
     сайзинги) — всегда; «редкое» (ante, dead cards, солверные
     параметры) — под спойлером. На главном экране только то, что
     влияет на решение или доверие к ответу.
  4. Базовый кегль >=14px; числа моноширинно (tabular); отступы по
     сетке 4/8; тёмная тема с контрастом >=4.5:1 текстового (факты:
     muted #b5b5b5 на #181818 = 4.2:1 и faint #858585 = 2.7:1 — подняты
     до #c9c9c9 = 9.6:1 и #a8a8a8 = 6.4:1).
  5. Карточные токены и цветкоды действий стандартизованы один раз:
     карта 40×56 (пропорция ~0.71 игральной карты), ранг крупно + масть
     графически, скругление, тень; классы fold/call/check/raise/push.
  6. Состояния продукта — экран-режимы, не «всё сразу»: «настраиваю» /
     «считаю» (прогресс с числом итераций) / «смотрю ответ» (матрица +
     инспектор) / «дриллю» (вопрос -> ответ -> разбор).
  7. Ноль модальных окон для основных потоков — панели.
  8. GW-скриншоты — референс пропорций/иерархии (центр ~55-60%, рейлы
     ~18-22% / ~20-25%, тонкий хедер), не макет для копирования.
     Ориентация матрицы (GW-стандарт): XYs выше диагонали
     (row=idx(X), col=idx(Y)); XYo зеркально ниже; пары на диагонали.
  Гэпы текущего UI к T4.1/T4.2 (факт верификации сессии 17): makeJob()
  не эмитит ни board, ни exploitability_samples (job-объект :771-800;
  отображение борда из result есть :996/:1141, задания нет) —
  закрывается в куске 2.

(4) Процесс приёмки: (а) двухшаговая: структурный макет (каркас:
размеры, расположение, серые блоки) -> утверждение геометрии ->
визуальный слой на утверждённой геометрии; UI не сдаётся «сделал,
посмотри» одним куском; (б) дефект-листы: каждый просмотр = список
дефектов с числами («ячейка 28px -> надо >=36»), не общее мнение;
(в) аннотации — на полях, не в кадре; (г) hero-экран «смотрю ответ»
одним кадром финальной достоверности с реальными данными — до
распространения языка на другие режимы (утверждён сессией 17).

(5) Порядок кусков: 0 каркас -> 1 визуал (hero-экран) -> 2 сборка
новой оболочки index.html (перенос существующих возможностей +
board/exploitability_samples) -> 3 движок (drill.rs шаговый +
/v1/drill/* + session-стор; параллелен 1-2) -> 4 дрилл-вкладка
(режим «дриллю») -> финальные гейты.

(6) Этапы UI (решение пользователя, сессия 17): (а) полировка —
плановый этап ПОСЛЕ завершения ядра; критерий входа — все данные фаз
4-6 доступны из UI (переменные борды/рунауты, ICM-слой, библиотека
спотов); это плановый этап с проверяемым критерием входа, не «потом
перепишем» (красный флаг №4 не срабатывает — этап в плане); (б)
функциональная достройка — остаётся в работе: дрилл-вкладка (reveal
после ответа, счёт, потеря EV — ядро D-003), поля board +
exploitability_samples в форме спота (данные T4.1/T4.2 в ядре есть,
UI обязан их отдавать), фикс багов, блокирующих использование;
деревянность/минимализм текущего UI — ожидаемы на этом этапе, чинится
только блокирующее; (в) UI-хвост ведётся списком дефектов в AI_LOG.
